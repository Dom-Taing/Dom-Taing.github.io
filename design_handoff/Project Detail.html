The Problem

Scattered accounts, no single source of truth.

Users were managing money across 5+ bank accounts and investment platforms, copying data into spreadsheets manually — a process prone to error and hours of wasted time each month.

Existing tools either required expensive subscriptions, felt cluttered, or had no real-time data — they were snapshots, not live views.

The Approach

Real-time sync, intelligent defaults.

I designed a microservices backend in Go that aggregates data from multiple financial APIs, normalizes it, and pushes live updates to the client via WebSocket connections. Each user's session maintains a dedicated stream.

The frontend was built in React with a tight focus on data density — showing the right numbers at a glance without overwhelming the user.

"The hardest part wasn't building the real-time pipeline — it was designing the data model to handle the wild inconsistencies between different banks' APIs."
Key Challenges

Scale without sacrificing speed.

At 50K users, naive database queries became the bottleneck. I introduced a multi-layer caching strategy: hot user data lives in Redis with a 30-second TTL, and a read replica handles historical queries.

WebSocket connections are managed by a stateless Go service with Redis pub/sub as the message broker — this makes horizontal scaling straightforward.

What I Learned

Latency is a product decision.

I shipped the MVP with synchronous data fetching on each page load. Users complained it felt slow even at 800ms. Switching to optimistic UI and background refresh made the app feel instant — even though the data took the same amount of time to arrive.

Perceived performance matters as much as measured performance.
